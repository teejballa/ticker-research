## Implementation Details

### Task 1: getSectorSigma60d (sector-mapping.ts)

Appended to existing file without touching `getSectorETF`. Fetches ~100 calendar days of ETF daily closes via `yf.historical()`, takes the last 61 rows → 60 daily returns, computes sample standard deviation (n-1 denominator). Returns null if <30 rows of history. Cached 24h via existing `cached()` Upstash helper with key `sector_sigma_60d:{etf}:{YYYY-MM-DD}`. `@knowable_at asOf` annotation is the magic string Wave 6's `check-feature-asof.ts` CI guard will grep for.

### Task 2: zscore.ts pure functions

Two exported functions, both fully unit-testable with no IO:
- `tickerRolling60dZ(value, history60d)` — sample z-score of `value` vs 60-day rolling history for the same ticker
- `crossSectionalZ(value, universeValues)` — sample z-score of `value` within today's universe

Cold-start contract: n<5 → return 0 + console.warn (prevents NaN/Inf in feature vectors during warm-up). Zero-variance contract: stdev=0 → return 0 + console.warn. Both carry `@knowable_at` annotations. 14 tests cover: numpy reference match (tolerance 1e-3), n<5, stdev=0, symmetry, n=5 exact boundary.

### Task 3: 36-feature space (learning.ts)

Additive extension — original `FEATURE_NAMES` and `buildFeatureVector12` are untouched:
- `FEATURE_NAMES_12` alias (same object reference as `FEATURE_NAMES`) for 36-d callers
- `FEATURE_NAMES_36`: 36 strings in three blocks of 12 (base / `_z60d` / `_zxs`); invariant guard throws at module load if count drifts
- `buildFeatureVector36(trace, techSnap, techPattern, history60d, universe)`: calls `buildFeatureVector12` for positions 0-11, then applies `tickerRolling60dZ` and `crossSectionalZ` per feature name using the provided Record slices
- `priorPrecisionForN(n)`: 8/4/1 annealing at n<100/n<500/n≥500 (D-19)

18 tests: structure invariants, back-compat positions, cold-start zeros, non-zero z with real history/universe data, precision schedule boundary cases.

### Task 4: computeLabelsFor + cron wiring

`src/lib/labels/compute.ts` is the single source of truth for all three labels (D-17):
- `is_directional_hit`: `sector_relative_pct > 0` (D-15)
- `is_sigma_hit_k1`: `classifyHit({..., sector_sigma: sigma_60d, k: 1})` (D-14 PRIMARY)
- `is_hit_flat1`: `classifyHit({..., threshold_pct: 1})` (D-16 tertiary, back-compat)
- `sector_sigma_60d`: snapshotted at call time from `getSectorSigma60d`

Both cron routes now import and call this single helper — zero parallel/forked label logic. Relabel's WHERE clause extended to `OR is_sigma_hit_k1 IS NULL` so existing rows with `sector_etf` already set get sigma labels on the next sweep. Both routes write all 4 new columns in the same `update`/`create` call. CRON_SECRET Bearer auth preserved on both routes.

8 tests verify: three-value combinations (2.5ppt, 0.5ppt, negative), null ETF path, null ETF + null sector_rel, getSectorSigma60d returning null, exact call args, single-call invariant.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Initial test used decimal units for sector_relative_pct (wrong system units)**
- **Found during:** Task 4 first test run
- **Issue:** Test used `sector_relative_pct: 0.025` (0.025 = 0.025 percentage-points, essentially zero) but expected `is_hit_flat1 = true` (which requires > 1 percentage-point). The system stores `sector_relative_pct` in **percentage-points** (2.5 = +2.5%) matching `pct_change = ((price - price_at_X) / price_at_X) * 100`. Initial test cases had decimal notation from the plan pseudocode.
- **Fix:** Updated test cases to use percentage-point units (2.5ppt, 0.5ppt, -2.0ppt). Updated test comments to document the unit convention explicitly.
- **Files modified:** `src/app/api/cron/__tests__/relabel-three-labels.test.ts`
- **Commit:** 53204cd (second version of the file, same commit)

**Note on plan pseudocode:** The plan's `sector_relative_pct: 0.025` in the test action section used decimal representation. The fix brings the tests in line with the actual system unit contract documented in `price-followup/route.ts` ("2.34 means +2.34%").
